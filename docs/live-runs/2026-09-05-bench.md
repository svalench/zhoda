# Decision bench 2026-09-05 (XOR slice 16)

Первый измеренный прогон `--suite decision`. Датасет **51** кейс
(`core/eval/bench/decision-50.jsonl`); live — **16 XOR architecture**,
arms `zhoda` / `majority` / `council`, таблица `compute` (`C = zhoda.requests`).
`--no-clarify`, `rounds_cap: 4`, свежий кэш `.zhoda-cache-bench.db`.
Тот же совет, что eval-пачки: gpt-4.1-mini / gemini-2.5-flash-lite /
deepseek-v4-flash.

Wall **35.7 мин**. Spend **$0.220** (zhoda $0.125 + majority $0.021 +
council $0.075). Логи gitignored:
`core/eval/runs/20260905-192517-bench/`. Сжатая копия в этой папке.

Судья — keyword-blind (`answer_options[0]` раньше в первых 500 символах).
Это не LLM-judge.

## Headline

| arm | accuracy | zhoda_rate | avg_dead_ends | dead_ends/$ | avg_req | avg_usd |
|---|---|---|---|---|---|---|
| zhoda (debate) | **16/16** | **1/16** | 0.06 | 8.0 | 43.9 | $0.0078 |

| council (single-pass, C-matched) | **15/16** | — | 0 | 0 | 43.9 | $0.0047 |

Единственный промах: council на `arch-pg-kafka` выбрал Kafka. Zhoda и
vote — PostgreSQL.

**MVP-гейт «Zhoda > однопроходного совета»** на этом срезе — один кейс
из шестнадцати. Keyword-accuracy на канонических XOR насыщена: все три
arm почти всегда называют тот же учебник. Разница протокола в другом:

- дебат **15/16 majority_at_cap** (карта тезисов, без плана);
- vote **16/16 zhoda** за 0 раундов (синтез pick, не спор);
- `dead_ends/$` выше у vote, потому что vote чаще *достигает* zhoda —
  отбраковка считается только на достигнутом консенсусе, не на расколе.

## Human subsample (4)

Читал `decision` целиком в `summary.json`, не только keyword.

**arch-pg-kafka.** Zhoda: PostgreSQL, ACID, команда из четырёх, Kafka
как отвергнутый путь (`dead_ends=1`). Majority — тот же pick (кэш
позиций, 2 req). Council: Kafka «designed for 50k RPS». Это как раз
тот кейс, ради которого протокол: совет масштабирует throughput,
дебат удерживает ops-constraint.

**arch-monolith.** Zhoda — dissent map «No zhoda (majority)» +
синтетическая оппозиция microservices; gold «monolith» первым.
Majority синтезирует чистый pick. Council: «Decision: Monolith.»
Keyword зачёл всех троих; по форме zhoda честнее (раскол), vote —
как council.

**arch-k8s-mvp.** То же: дебат majority_at_cap + synthetic Maximalists;
vote/council — single VM. Gold первым у всех.

**arch-sqlite-internal.** Zhoda: SQLite, но в том же тезисе hedged
«PostgreSQL can offer simpler…» — foil во второй половине, gold
первым. Majority — чистый SQLite + `dead_ends=1`. Council — SQLite.

## Confound: общий кэш

Один `OpenRouterProvider` на все arms. Majority после zhoda:
**2–3 HTTP + ~7.5 cache hits**. Это «те же позиции, без раундов»,
не независимый vote с нуля. Accuracy vote из-за этого ближе к zhoda.
Council промпты другие — кэш 0, сравнение честнее.

## Что это не закрывает

- Остальные 35 кейсов датасета (security/ops/sycophancy/minority) не
  гонялись live.
- Нет SC / best-of-N и cost-matched таблицы.
- Нет LLM-judge: keyword зачтёт dissent map, если gold option первое.
- `dead_ends/$` на majority_at_cap почти всегда 0 — метрика молчит
  как раз там, где дебат честно не сошёлся.

Следующий прогон: 51 live или хотя бы 16 security/ops XOR; отдельный
кэш на arm; LLM-judge на kafka-класс (оба варианта в тексте).

## Blind LLM rescore (тот же arch-16)

`rescore` по полным `decision`, arm name скрыт, зачёт только
*committed* pick. Таблица: [arch-16-llm.tsv](2026-09-05-bench/arch-16-llm.tsv).

| arm | keyword acc | **LLM committed** | zhoda_rate |
|---|---|---|---|
| zhoda | 16/16 | **1/16** (только kafka, где zhoda_reached) | 1/16 |
| majority | 16/16 | 15/16 | 16/16 |
| council | 15/16 | **15/16** (тот же kafka→Kafka) | — |

Keyword зачитывал dissent map, если gold шёл первым. LLM так не делает:
15/16 дебатов — «No zhoda (majority)» → miss. Majority-промах LLM:
`arch-monolith` (vote всё ещё упоминает microservices в том же абзаце).

Под keyword MVP-гейт «Zhoda > council» — ничья 16 vs 15. Под committed
pick **council 15/16 > zhoda 1/16**: дебат честно не коммитится.
Это не баг судьи — это `majority_at_cap`.

Кэш по arm с этого коммита изолирован (`cache-zhoda.db` /
`cache-majority.db`). Arch-16 majority дешевизна (2–3 req) — старый leak.

## Slice 2: remaining XOR-16 (isolated cache + live LLM judge)

`--kind xor --offset 16 --limit 16`: 4 leftover architecture + 8 security +
4 ops. Arms те же, **отдельный sqlite на arm**, `--judge llm` на каждом
результате. Wall **39.3 мин**, spend **$0.265** (zhoda $0.139 / majority

Zhoda committed только там, где реально zhoda: `sec-argon2` (Argon2id),

database-per-tenant. Majority промах: `sec-admin-2fa` → «Skip 2FA»
(временная мера) — LLM rightly refused.

## XOR-10 post-guard (loaded-premise + XOR-pick)

**MVP-гейт «Zhoda ≥ council» на committed XOR-pick закрыт: 10/10 = 10/10.**
