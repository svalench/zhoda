# Слой 1: zhoda-core — движок дельберации

> Python / FastAPI. Независимое ядро: не знает ни про dsh, ни про MCP.
> Вход — вопрос пользователя, выход — вердикт + minority report + хроніка.

## 1. Пайплайн одного вопроса

```
вопрос пользователя
      │
      ▼
┌─────────────┐   2–4 вопроса пользователю    ┌──────────────┐
│ СТАДИЯ 0    │ ────────────────────────────► │  КАРТА       │
│ Элиситация  │ ◄──────────────────────────── │  ЦЕННОСТИ    │
└─────────────┘      ответы пользователя      └──────────────┘
      │
      ▼
┌─────────────┐   N независимых позиций (JSON-stance, анонимно)
│ СТАДИЯ 1    │
│ Позиции     │
└─────────────┘
      │
      ▼
┌─────────────┐   кластеризация позиций → фракции + «независимые»
│ СТАДИЯ 2    │
│ Фракции     │
└─────────────┘
      │
      ▼
┌─────────────┐   раунды: аргумент → контраргумент → перекрёстный
│ СТАДИЯ 3    │   допрос; модель может ПЕРЕЙТИ в другую фракцию
│ Дебаты      │   (публично, с указанием убедившего аргумента)
└─────────────┘
      │
      ▼
┌─────────────┐   детерминированная проверка по JSON-вердиктам;
│ СТАДИЯ 4    │   адаптивная остановка (згода или кап раундов);
│ Згода       │   слабый консенсус → эскалация на ступень выше
└─────────────┘
      │
      ▼
┌─────────────┐   вердикт большинства + minority report + карта
│ СТАДИЯ 5    │   разногласий + полная хроніка; результаты
│ Вердикт     │   уходят в репутационный рейтинг
└─────────────┘
```

## 2. Стадия 0 — элиситация (ключевое отличие)

Проблема, которую закрываем: LLM фабрикуют ответ вместо уточняющего вопроса.
Большинство неверных ответов — это ответы на неверно понятый вопрос
(solution-jumping).

Механика:

1. Все модели совета получают сырой запрос и возвращают **не ответ**, а список
   неясностей: `{ambiguity, why_it_matters, candidate_question}`
2. Агрегатор выбирает 2–4 вопроса с наибольшим влиянием на ответ
   (приоритет: вопросы, от ответа на которые позиции расходятся сильнее всего)
3. Пользователь отвечает → строится карта ценности
4. Дебаты могут приостановиться и запросить уточнение посреди спора
   («фракции разошлись, и ответ зависит от того, что вы имели в виду под X»)

```python
class ValueMap(BaseModel):
    goal: str                    # зачем: какое решение примут по ответу
    success_criteria: list[str]  # критерии хорошего ответа
    constraints: list[str]       # бюджет, сроки, стек, запреты
    anti_goals: list[str]        # что точно НЕ нужно
    open_ambiguities: list[str]  # оставшиеся неясности (для minority report)
```

Режимы: `--no-clarify` (пропустить стадию), `--auto-clarify` (модель сама отвечает
на вопросы правдоподобными дефолтами и помечает их как допущения).

## 3. Стадии 1–2 — позиции и фракции

Каждая модель отвечает структурированно:

```python
class Position(BaseModel):
    thesis: str                  # суть позиции в 1–2 предложениях
    answer: str                  # полный ответ
    arguments: list[str]         # ключевые аргументы
    falsifiability: str          # при каких условиях позиция неверна
    confidence: float            # 0..1
```

Кластеризация во фракции:

1. Эмбеддинги `thesis` + `arguments` → косинусная близость
2. Порог слияния — параметр конфига (default 0.82, подобрать на тестах)
3. Фракция из 2+ моделей вырабатывает платформенный ответ (внутренний раунд);
   одиночки — «независимые»
4. Фракции получают имена от председателя: «Прагматыкі», «Максімалісты»...

## 4. Стадия 3 — дебаты (оксфордский формат)

Один раунд:

1. Каждая фракция выдвигает аргумент против сильнейшей оппонирующей фракции
2. Оппонент отвечает контраргументом
3. Перекрёстный допрос: фракция обязана ответить на конкретную претензию
   (не «ранжируй», а «найди фактическую или логическую дыру»)
4. Штатный оппонент (devil's advocate): одна модель по ротации обязана
   атаковать лидирующую позицию — защита от сикофантного сговора
5. Голосование о переходе: модель может сменить фракцию, указав убедивший аргумент

```python
class Critique(BaseModel):
    target_faction: str
    flaw_type: Literal["factual", "logical", "scope", "values_mismatch"]
    claim: str                   # конкретное утверждение, с которым спорим
    rebuttal: str

class FactionSwitch(BaseModel):
    model: str
    from_faction: str
    to_faction: str
    convinced_by: str            # цитата аргумента
```

## 5. Стадия 4 — згода и остановка

- Схождение считается по структурированным вердиктам (сравнение `thesis` после
  каждого раунда), НЕ по похожести текстов
- Адаптивная остановка: згода → стоп; иначе кап раундов
  (исследования: обычно хватает 2–3, кап 4)
- Сила консенсуса: `unanimous` / `majority` / `split` / `deadlock`
- При `split/deadlock` и включённой эскалации — апелляция на ступень выше
  по лестнице моделей; председатель выносит решение по хроніце

## 6. Стадия 5 — вердикт

```python
class Verdict(BaseModel):
    decision: str                # ответ большинства
    zhoda_reached: bool          # достигнута ли згода
    consensus_strength: Literal["unanimous", "majority", "split", "deadlock"]
    value_map: ValueMap          # против чего проверялось
    minority_report: str | None  # позиция меньшинства — сохраняется!
    dissent_map: list[Disagreement]   # где и почему разошлись
    switches: list[FactionSwitch]     # кто и почему изменил позицию
    rounds_taken: int
    cost: CostReport             # запросы, токены, кэш-хиты
    transcript_id: str           # ссылка на полную хроніку
```

## 7. Репутация (после MVP)

- ELO-рейтинг моделей по доменам задач: чья критика принята (+), чьи ошибки
  подтвердились (−), чьи переходы оказались к лучшему (+)
- Влияет на: состав совета под задачу, вес голоса при консенсусе
- Хранилище: SQLite (локально) / PostgreSQL (сервер)
- Это дата-моат проекта: со временем Zhoda знает, какой модели в каком
  домене можно доверять

## 8. Технические решения

- **Стек:** Python 3.12+, FastAPI, async httpx, Pydantic v2, uv
- **Параллелизм:** `asyncio.gather(return_exceptions=True)` — graceful
  degradation: упавшая модель исключается из раунда, ошибка только если упали все
- **Кэш:** семантический кэш на уровне стадий (позиции кэшируются по
  hash(question + value_map + model)); переиспользовать llm-cache-router
- **Хранение хронік:** JSONL-файлы (простота, как у Карпаты) с опцией PG
- **Конфиг совета:** YAML — состав, лестница эскалации, кап раундов, пороги

```yaml
# zhoda.yaml — пример
council:
  - deepseek/deepseek-chat-v3:free
  - google/gemma-3-27b:free
  - qwen/qwen3-32b:free
  - meta-llama/llama-4-scout:free
chairman: google/gemini-3-pro        # для апелляций (платный, опционально)
rounds_cap: 4
faction_threshold: 0.82
devils_advocate: true
escalation:
  enabled: false                      # true = платная апелляция
  ladder: [free, mid, frontier]
budget_per_question_usd: 0.0          # жёсткий предел расхода
```

## 9. API ядра (черновик)

```
POST /v1/clarify          → вопросы к пользователю | ValueMap (если --no-clarify)
POST /v1/deliberate       → полный цикл → Verdict (SSE-стрим стадий)
GET  /v1/transcript/{id}  → полная хроніка дебатов
GET  /v1/reputation       → рейтинг моделей по доменам
GET  /v1/health
```
