# Разбор возражений по дизайну (23.08.2026)

> Внешний design review протокола Zhoda: 7 возражений, 5 рекомендаций.
> Итог: 5 принято полностью, 2 частично, 1 отклонено. Ниже — по пунктам,
> с указанием, что именно меняется в документах и протоколе.
> Раунд 3 (по коду) — в конце документа.

## 1. «Debate or Vote» работает против нас → ПРИНЯТО

Возражение: дебаты — не универсальное улучшение; для многих задач голосование /
self-consistency даёт тот же результат в разы дешевле.

Решение:

- **Протокол-роутер** на входе: классификатор определяет класс задачи
  (`factual_lookup`, `reasoning`, `decision`, `code_review`, `creative`) и
  выбирает протокол: `vote` (дешёвый, self-consistency), `debate`, `red_team`.
- Целевой класс, где дебаты сильнее голосования: **decision-задачи** — выбор
  архитектуры, библиотеки, подхода. Там ответ зависит от недосказанных
  ограничений (стадия 0!) и trade-off'ов, которые и вскрывает спор фракций.
- Изменения: docs/01-core.md §1.5 (роутер), вайтпейпер v0.2.

## 2. Капитуляция и конформизм агентов → ПРИНЯТО

Возражение: модели капитулируют перед уверенным большинством, даже когда правы
(RECONCILE); конформизм переворачивает позиции не всегда к лучшему. Фракции
могут как лечить, так и усугублять (искусственная поляризация).

Решение — четыре механики:

1. **Обоснование фракций**: фракции формируются снизу — кластеризацией реальных
   позиций, а не назначением ролей. Искусственной поляризации нет: согласные
   объединяются, одиночки остаются независимыми.
2. **Переход только через провал**: модель меняет фракцию, только если её
   контраргумент провалился И она цитирует убедивший аргумент. «Просто согласен»
   протоколом не принимается.
3. **Stability-правило**: консенсус считается достигнутым, если согласие
   продержалось 2 раунда подряд (защита от случайного флипа).
4. **Анти-капитуляция в репутации**: переход, после которого новая позиция
   оказалась ошибочной, штрафует сильнее, чем ошибочная, но удержанная позиция.

Изменения: docs/01-core.md §4 (переходы), §5 (stability), §7 (репутация).

## 3. «Себестоимость ноль» — самообман → ПРИНЯТО

Возражение: бесплатные модели = rate limits и слабое качество; дебат ограничен
снизу слабейшим участником; стоимость переносится на пользователя и latency.

Решение:

- Честная формулировка везде: «инфраструктурная себестоимость ноль; токены —
  BYOK пользователя, с явной оценкой стоимости и времени ДО запуска».
- Слабое звено: состав совета взвешивается репутацией; слабый консенсус
  эскалируется к сильным моделям (лестница). Бесплатный тир — демо и личное
  использование, не SLA.
- Latency — часть продукта, а не баг: позиционирование «инструмент второго
  мнения для тяжёлых вопросов», прогресс стримится по раундам.
- Признаём в документах: 5 раундов слабых моделей могут уверенно сойтись
  неправильно — именно поэтому бенчмарк (п. 7) в составе MVP, а не после.

Изменения: docs/master-plan.md §5, docs/02-mcp-server.md (estimate — уже есть).

## 4. Стадия 0 раздражает пользователей → ПРИНЯТО

Возражение: пользователи ненавидят отвечать на вопросы до получения ответа.

Решение:

- Дефолтный режим `smart`: элиситация всегда идёт, но вопросы задаются,
  только если ambiguity-score выше порога; иначе совет отвечает сразу,
  пометив допущения в вердикте (`assumptions[]`).
- Вопросы приходят с вариантами ответов (one-tap), а не открытым полем.
- Режимы `--no-clarify` / `--auto-clarify` остаются.

Изменения: docs/01-core.md §2.

## 5. Land-grab на чужой платформе + двуязычный стек → ЧАСТИЧНО

Возражение: DeepSeek может встроить дебаты в сам dsh; core на Python, а dsh —
TS/Cordis; одному человеку тяжело.

Решение:

- Порядок сборки: **core → MCP → dsh-плагин**. MCP — это и есть страховка:
  dsh поддерживает MCP-серверы, значит `zhoda-mcp` даёт интеграцию с dsh
  бесплатно, плюс Claude Code и Codex тем же артефактом. Если DeepSeek встроит
  дебаты — MCP-слой живёт независимо.
- Перенос core на TypeScript — **отклонено**: кластеризация фракций — это
  эмбеддинги и ML-инструментарий (Python-экосистема сильнее), основной стек
  автора — Python/FastAPI, а TS-поверхность ограничена тонким плагином
  (правило «плагин = оболочка»). Двуязычность минимизирована архитектурой.

Изменения: docs/master-plan.md §7 (порядок этапов).

## 6. AGPL для core-библиотеки → ПРИНЯТО

Возражение: AGPL на библиотеке отпугнёт интеграторов; классика — core под
MIT/Apache, сервер под AGPL.

Решение — сплит-лицензия:

| Часть | Лицензия | Почему |
|---|---|---|
| `zhoda_core` (движок) | Apache-2.0 | Максимум интеграций |
| `zhoda-mcp`, плагины | Apache-2.0 | Каналы распространения, не трогаем |
| API-сервер (`api/`) | AGPL-3.0 | Защита от облачных клонов |

Моат — не код, а репутационные данные, бренд и комьюнити.

Изменения: README.md, docs/master-plan.md §6, LICENSE-файлы при первом коде.

## 7. Нет валидации и дистрибуции → ПРИНЯТО

Возражение: 24k★ у llm-council — эффект имени; аналоги без имени имеют 0–134★.
Нет ответа «как измерим, что дебаты лучше» и «кто первые 100 пользователей».

Решение:

- **Бенчмарк с первого дня** — в составе Core MVP, не после: фиксированный набор
  из 50–100 decision-задач с рубриками; руки: одна модель / однопроходный совет
  (карпаты-стайл) / Zhoda полный / Zhoda без стадии 0 / Zhoda без фракций.
  Метрики: рубрик-скор, калибровка, стоимость, latency.
- **Киллер-кейс**: вердикты по архитектурным решениям в коде (ADR-ревью,
  «рефакторить X или Y», выбор библиотеки). Там живёт dsh/Claude Code
  аудитория и качество измеримо.
- **Первые 100 пользователей**: dogfooding в своих проектах → MCP-реестры →
  awesome-dsh-plugin → статья с цифрами бенчмарка («+X% против однопроходного
  совета») на Dev.to и r/LocalLLaMA. Бенчмарк — это и есть контент для
  дистрибуции.

Изменения: docs/master-plan.md §7–8, §10 (новый раздел), docs/01-core.md §10.

## Что НЕ меняется

- Трёхслойная архитектура (но порядок сборки: core → mcp → plugin)
- Фракции, оксфордские раунды, devil's advocate, minority report
- Донаты без токена
- Имя, домен, бренд

# Раунд 3 — ревью кода (23.08.2026)

> Ревью первого живого кода: 3 бага в провайдере, 4 дизайн-проблемы.
> Итог: принято всё, исправлено кодом и тестами в том же коммите.

## 3.1. Баги openrouter.py → ИСПРАВЛЕНО

1. **429 без ретрая** — на free tier 429 это чаще транзиентный rate limit
   (20 req/min), а не дневная квота. Теперь: `RateLimitError` (Retry-After +
   бэкофф) отделён от `QuotaExceededError` (только после исчерпания ретраев);
   семафор конкурентности (default 4).
2. **Бюджетный кап — фикция**: `usage` не парсился. Теперь токены и usd
   накапливаются из каждого ответа; `budget_usd=0` блокирует не-`:free`
   модели ДО вызова.
3. **Ретраи на всё**: ретраим только 429/5xx/сетевые; прочие 4xx — фейл сразу.

Тесты: `core/tests/test_openrouter.py` — 5 тестов на мокнутом транспорте.

## 3.2. Self-reported confidence роутера → ИСПРАВЛЕНО

Самооценка уверенности LLM некалибрована (0.85–0.95 всегда) — fail-safe бы
не сработал никогда. Теперь классифицируют ДВЕ разные модели: согласие =
confidence 1.0, разногласие = эскалация вверх (дебаты). «Самооценка» заменена
«межмодельным согласием» — роутер следует философии проекта.

## 3.3. validate_switch обходится → ИСПРАВЛЕНО

- Возражения получают ID и гейт качества: factual/logical — конкретный claim;
  scope/values_mismatch — обязательные `specifics` (что именно не учтено).
  Спам расплывчатыми претензиями не проходит гейт.
- `FactionSwitch.objection_id` ссылается на конкретную открытую претензию;
  сфабрикованная строка больше не работает.

## 3.4. Рекурсия доверия → ПРИЗНАНО ЧЕСТНО

Zhoda не устраняет доверие к моделям — она концентрирует его в трёх
аудируемых точках: классификация роутера, закрытие возражений, попарное
сравнение позиций. Каждая — отдельный логируемый вызов в хроніце.
Зафиксировано в docs/01-core.md §7.5.

## 3.5. Docstring впереди кода → ИСПРАВЛЕНО

- Появились реальные `transcripts.py` (JSONL-хроніка) и `anonymize.py`
  (алиасы с перетасовкой) — инварианты больше не только на словах.
- В bench — seed-датасет `tasks.jsonl` (3 задачи с рубриками, растёт до
  50–100): «published in this directory» теперь правда.
